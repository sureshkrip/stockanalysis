# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Note

Per CONTEXT.md decision **D-12**, Phase 1's frontend is deliberately a **minimal health/status page** — proof that the Next.js app can reach the FastAPI backend (`GET /companies`). It is NOT the data-table/screener UI (that's Phase 2+). This contract is scoped accordingly: one server-rendered readout, zero forms, zero tables, zero destructive actions, zero client-side interactivity.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (shadcn init explicitly deferred — see rationale below) |
| Preset | not applicable |
| Component library | none — plain Next.js App Router Server Component, no UI kit |
| Icon library | none — two states (healthy/error) are conveyed via color + text, not iconography, at this scope |
| Font | Geist Sans (Next.js `create-next-app` default via `next/font/google`) — no custom brand typography needed for a single status readout |

**shadcn gate decision (discretionary, documented per CONTEXT.md's "Claude's Discretion" note on internal scaffolding details):** No `components.json` exists in this greenfield repo, and the tech stack is Next.js (App Router) per RESEARCH.md — the shadcn init gate would normally fire here. It is intentionally **deferred to Phase 2** instead of run now: Phase 1's entire UI surface is one server-rendered text readout with no forms, buttons, tables, or interactive controls (D-12), so initializing a component library now would install tooling with zero components actually needed this phase. Phase 2 (`BROWSE-01`, the sortable company table) is where a real component library (table, sort controls, badges for trust indicators) is first needed — run the shadcn init gate there instead, against real component requirements. This keeps Phase 1's dependency footprint matched to its proof-of-wiring goal.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | regular (400) | 1.5 |
| Label | 14px | regular (400) | 1.4 |
| Heading | 24px | semibold (600) | 1.2 |
| Display | 32px | semibold (600) | 1.2 |

Usage:
- **Display (32px/600):** the company count number itself (e.g., "56") — the single most important number on the page.
- **Heading (24px/600):** page title, "Data Center Stocks".
- **Body (16px/400):** status sentence ("API: healthy" / "API unreachable").
- **Label (14px/400):** secondary metadata line (as-of timestamp, backend URL in error state).

Only 4 sizes, 2 weights declared — no other combinations permitted this phase.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Page background |
| Secondary (30%) | `#F4F5F7` | Status card surface (the one content block on the page) |
| Accent (10%) | `#16A34A` (green) | The "healthy" status indicator only — dot/badge + "API: healthy" text |
| Destructive | `#DC2626` (red) | The "unreachable/error" status indicator only — dot/badge + error text |

Accent reserved for: the healthy-state status dot and the healthy-state status text. Nothing else on this page uses the accent color (no buttons, links, or other interactive elements exist this phase).

Destructive reserved for: the error-state status dot and the error-state status text only. There are no destructive user actions in this phase (read-only page) — this color communicates system failure state, not a user-triggered destructive action.

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Applicable state considerations resolved: 7 covered, 0 backstop, 1 unresolved

**Element:** `status-readout` — server-rendered text block showing company count + API health, sourced from `GET /companies` (or `/health`) fetched server-side in a Next.js Server Component. Classified as `list-collection` (count is derived from the companies collection) + `static-content` (rendered as fixed text, no per-item list UI).

**Element:** `page-title` — fixed short string "Data Center Stocks". Classified as `static-content`.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | status-readout | ✅ covered | 0 companies returned renders the "No companies tracked yet" copy + next-step guidance (see Copywriting Contract → Empty state) |
| loading | status-readout | ✅ covered | Page is a Server Component; the fetch to the backend resolves before the response is sent to the browser — there is no client-visible in-flight spinner by design. An explicit fetch timeout (recommend 5s) must be set so a hung backend call falls through to the Error state rather than hanging the page render indefinitely |
| error | status-readout | ✅ covered | Non-200 response or fetch failure/timeout renders "API unreachable" copy + retry-by-refresh instruction (see Copywriting Contract → Error state) |
| populated | status-readout | ✅ covered | N>0 companies renders the green healthy indicator + pluralized count line (see Copywriting Contract → Healthy state) |
| partial | status-readout | ⚠ unresolved | Per-ticker ingestion failures (STORE-02's failure log) do not change this page's aggregate state — any 200 response from `/companies` is treated as "populated" regardless of how many individual companies have null price/fundamentals fields. Planner assumption: acceptable per D-12's scope (this is a proof-of-wiring page, not a data-quality dashboard); surfacing per-company data completeness is out of scope until Phase 2's trust indicators (TRUST-01/02) |
| overflow | status-readout, page-title | ✅ covered | Company count is a bounded small integer (0-999 range for this ~56-ticker universe) and the page title is a fixed short string — neither can overflow its container; no truncation/wrap handling required |
| zero-one-many | status-readout | ✅ covered | Singular/plural copy declared: "1 company tracked" vs. "56 companies tracked" (see Copywriting Contract) |
| long-text | status-readout, page-title | ✅ covered | No user-generated or variable-length text exists on this page — all copy is fixed, short, and pre-written; no truncation/ellipsis strategy needed |
