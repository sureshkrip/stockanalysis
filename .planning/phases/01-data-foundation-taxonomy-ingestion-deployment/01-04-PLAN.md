Extend `backend/app/ingest/fundamentals.py` with market-cap derivation.

There is no market-cap concept in either XBRL taxonomy — RESEARCH.md verified this directly against NVDA's live companyfacts response. Market cap must be computed. Do not substitute the `dei` namespace's public-float concept:
<!-- planner-discipline-allow: EntityPublicFloat -->
`EntityPublicFloat` is reported only once a year, as of a non-period-end date, and excludes affiliate-held shares, so it is a materially different figure that would quietly skew every valuation comparison built on it in Phase 4.

Implement `find_nearest_close(session, ticker, as_of) -> Decimal | None` selecting the `Price` row for that ticker whose `as_of` has the smallest absolute distance to the requested date. Return `None` when the ticker has no price rows. Push the ordering into the query rather than loading the full series into Python.

Implement `compute_market_cap(shares_entry, session, ticker) -> Decimal | None` reading the shares entry's `end` field as the as-of date, looking up the nearest close, and returning the product. Return `None` when no close is available. A null market cap is the honest representation of "we could not compute this"; returning zero would make the company look free in every downstream screen, which is a far worse failure than a visible gap.

Perform the multiplication in `Decimal`, not float. Share counts reach the tens of billions (NVDA's verified entry is 24,300,000,000) and prices carry fractional cents; a binary float product introduces drift in the low-order digits of a figure that later phases rank companies against. Apply no rounding at ingest — the stored value is the full-precision product, and any display rounding is a presentation concern.

Wire the derivation into `extract_fundamentals` so each FactRow's `market_cap` is populated where a shares entry matching that filing exists. Match the shares entry to the filing by accession number where possible, falling back to the shares entry nearest the filing's period end. Leave `market_cap` as None where neither the shares figure nor a price is available.

Note that `extract_fundamentals` now needs database access for the price lookup — pass the session in as a parameter rather than opening one inside the extraction module, so the function stays testable and the caller owns transaction scope.

Extend `backend/tests/test_fundamentals.py` with the behavior bullets above, seeding a small price series in the `db_session` fixture.

  <action>
Add `write_fundamentals(session, ticker, rows)` to `backend/app/ingest/fundamentals.py`.

Persist with insert-or-ignore semantics on the `uq_fundamental_period_filing` constraint — the four-column key `(ticker, fiscal_year, fiscal_period, accession_number)`. Use the dialect-appropriate on-conflict-do-nothing construct, selected from the engine dialect so the same code path works on both SQLite and Postgres (STORE-01's premise is that the database swap requires no code change).

Do not key this write on ticker alone or on ticker plus fiscal year. RESEARCH.md Pitfall 5 is explicit that "just update the row for this ticker" is the natural instinct and is correct for prices but wrong here: it replaces prior periods on every run and eventually leaves a single row per company, silently violating D-09's requirement that the full 3-5 year history be ingested. The observable symptom is a per-ticker fundamentals count that stays flat near one instead of growing into the double digits, and by the time anyone notices, the fix is a re-ingestion project.

Insert-or-ignore rather than update-on-conflict is deliberate. When SEC later posts a restatement it arrives under a new accession number, so it inserts as an additional row and both the original and the restated figures survive. Overwriting on conflict would destroy the original figure — the exact thing point-in-time storage exists to prevent.

Now extend `run_refresh` in `backend/app/ingest/refresh.py`. Add the fundamentals work inside the existing per-ticker loop from plan 02; do not add a second pass over the tickers, which would double the wall-clock time and split the failure log across two conceptual runs.

Per ticker, in its own try/except separate from the price block:
1. Resolve the CIK. On `CikNotFoundError`, record a failure at stage `"cik"` and skip the fundamentals stage for this ticker only.
2. Fetch companyfacts, extract fundamentals, and write them. On any exception, record a failure at stage `"fundamentals"` and continue.

The price and fundamentals stages must fail independently: a ticker whose price fetch failed still gets its fundamentals attempted, and vice versa. Coupling them would mean one flaky provider silently halves the data collected from the other.

Commit per ticker after both stages, so an interrupted run leaves every already-processed ticker durably persisted and a re-run completes the remainder without duplicating what is already committed — which the insert-or-ignore semantics guarantee.

Extend `backend/tests/test_refresh.py` with the behavior bullets above. Include an explicit idempotency test running the full refresh twice against mocked providers and asserting the fundamentals row count is identical after both runs.
