Write `backend/app/ingest/refresh.py` implementing the orchestrator that Coolify's scheduled task invokes in plan 05.

Define a `TickerFailure` dataclass with `ticker: str`, `stage: str`, `error: str`.

Implement `run_refresh(session, taxonomy_path) -> RefreshResult` following RESEARCH.md Pattern 1's structure exactly:
1. Load and validate the taxonomy, then sync it to the tickers table. A taxonomy validation error is a legitimate hard failure — it means the owner's edit is malformed and there is nothing meaningful to ingest — so it may propagate. This is the one exception to the never-abort rule.
2. Generate a `run_id` (UUID) and record `started_at`.
3. Iterate tickers in taxonomy order. Wrap each ticker's price fetch-and-write in its own try/except catching broad `Exception`, appending a `TickerFailure` and `continue`-ing on error. Under no circumstance may a per-ticker exception propagate out of the loop — STORE-02 is violated the moment one ticker's failure ends the run, and RESEARCH.md's Anti-Patterns section names first-failure abort explicitly.
4. Commit per ticker rather than once at the end, so an interrupted or killed run leaves every already-processed ticker durably persisted rather than rolling back the whole batch.
5. After the loop, call `persist_refresh_log(session, run_id, failures, attempted)` writing one `RefreshLog` row with `run_id`, `started_at`, `finished_at`, `tickers_attempted`, `failure_count`, and the serialized `failures` list. This write happens on every run including a fully-clean one — a run with zero failures still writes its row, so the owner can distinguish "ran clean" from "never ran".

Append failures in iteration order and never deduplicate or merge them. Two different tickers failing at the same stage are two independent facts the owner needs to see; collapsing them would hide the scale of a systemic outage.

Log each failure through the standard `logging` module at WARNING with the ticker and reason as structured fields. Do not remove or deactivate a ticker on failure — per D-02a, delisted tickers stay in `sectors.yaml` and in the tickers table permanently, and the per-run failure log is precisely the intended safety net between the owner's roughly-monthly manual taxonomy reviews. There is no automated liveness check in this phase (D-02).

Add a `if __name__ == "__main__":` entrypoint so the module is invocable as `python -m app.ingest.refresh`. It opens a session, calls `run_refresh`, prints a one-line summary of attempted/succeeded/failed counts, and exits with status 0 when the run completed — even with failures present. A non-zero exit is reserved for a genuine orchestration failure (taxonomy invalid, database unreachable), because Coolify's scheduled-task UI surfaces non-zero exits as alerts and per-ticker failures are expected steady-state noise, not alertable conditions.

Write `backend/tests/test_refresh.py` covering every behavior bullet above, with the price fetcher mocked so failures are injectable deterministically. Name the primary isolation test `test_partial_failure_continues` — 01-VALIDATION.md's per-task verification map references that exact node id.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-06 | Denial of Service | `fetch_price` outbound calls | high | mitigate | Every provider call is bounded by an explicit timeout and by tenacity's `stop_after_attempt(3)`; a hung or persistently-failing endpoint costs one ticker, not the batch. Without this a single unresponsive request stalls the nightly run indefinitely (self-inflicted DoS per RESEARCH.md Security Domain). |
| T-01-07 | Denial of Service | 55-ticker retry storm against a rate-limited provider | medium | mitigate | Batch `download()` over the full list instead of per-symbol loops, plus `wait_exponential_jitter` so retries desynchronize rather than forming a thundering herd. |
| T-01-08 | Tampering | provider response values written to `prices` | low | accept | Values are coerced to `Decimal` and constrained by the Numeric column and the `(ticker, as_of)` unique key; a malicious provider could serve wrong prices, but the provider is already the trusted source of record for this data class and no cross-validation source exists within the $0 budget. Accepted for a personal research tool. |
| T-01-09 | Repudiation | ingestion runs with no audit trail | medium | mitigate | Every run writes a `RefreshLog` row — including fully-clean runs — recording run_id, timestamps, attempt count, and the ordered failure list, so "did tonight's refresh run and what did it miss" is always answerable. |

ASVS level 1; blocking threshold `high`. The single `high` threat (T-01-06) is mitigated with an acceptance-criteria gate on the bounded retry configuration.
