Remove the locally-published frontend port mapping in favor of Coolify assigning the external domain through its reverse proxy, which also terminates TLS. Keep the backend with no exposed port and no assigned domain — the frontend reaches it internally at `http://backend:8000`, and leaving the backend unexposed is the practical access control for an API that has no application-level auth. Do not add a `networks:` block; Coolify auto-creates a shared network per compose stack.

In Coolify this must correspond to a persistent volume configured in the backend service's Storages panel — without it the database is inside the container layer and every redeploy silently starts from an empty database, which looks exactly like a failed ingest.

Coolify's scheduled tasks expose no timezone override and standard five-field cron cannot express a DST-aware local time, so a fixed UTC time is chosen instead. `0 2 * * *` is 9pm EST and 10pm EDT — comfortably after the 4pm ET close and after same-day EDGAR filing processing under both DST states. This is a deliberate fixed-UTC choice, not a literal 9pm ET.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public internet → Coolify reverse proxy → frontend | the assigned domain is reachable by anyone who learns the URL |
| public internet → backend | mitigated to no boundary: the backend has no exposed port or domain |
| Coolify env-var store → running containers | secrets are injected at runtime rather than committed |
| container filesystem → host persistent volume | the SQLite system of record lives on host storage |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-20 | Information Disclosure | publicly-reachable `GET /companies` | medium | accept | Multi-user auth is locked out of v1 scope by REQUIREMENTS.md and the data is already-public SEC filings and market prices. Mitigated in depth by not exposing the backend at all — only the frontend has a domain. The owner is presented with the Coolify-level IP-allowlist and proxy-basic-auth options at the blocking checkpoint and records an explicit decision, so this is a consciously accepted risk rather than an unexamined default. |
| T-01-21 | Information Disclosure | secrets committed to the repository | high | mitigate | All values flow through `${VAR}` substitution sourced from Coolify's environment-variable UI; `.env` is gitignored from plan 01; `.env.example` carries placeholders only. Gated by an acceptance-criteria grep against the committed compose file. |
| T-01-22 | Denial of Service | VPS outbound egress blocked to SEC or the price provider | high | mitigate | Verified explicitly from inside the deployed container at the blocking checkpoint before the scheduled task is relied upon. RESEARCH.md flags this as Open Question 3 — unknowable without access to the owner's VPS network configuration, and silently fatal to every ingest run if unverified. |
| T-01-23 | Tampering | redeploy wiping the database | high | mitigate | SQLite lives on a Coolify persistent volume mounted at `/data`, not in the container layer. The checkpoint verifies durability empirically by comparing company counts across an actual redeploy — the failure mode is silent and looks identical to a failed ingest. |
| T-01-24 | Elevation of Privilege | the scheduled task executing inside the long-running API container | low | accept | Coolify's native scheduled tasks execute in the already-running service container by design (D-10 chose this over a cron sidecar). The refresh code is first-party and the container already holds the same database credentials, so no privilege boundary is crossed. |

ASVS level 1; blocking threshold `high`. All three `high` threats (T-01-21, T-01-22, T-01-23) carry `mitigate` dispositions, verified at the blocking human checkpoint since they depend on the owner's infrastructure.
